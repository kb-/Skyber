# Kyber media upstream comparison

**Status:** Source audit in progress. Runtime capture, encode, transport, decode, presentation, synchronization and performance proofs remain open.
**Reviewed:** 2026-11-22
**SDK:** Kyber 0.29.0, SDK tag commit `ebca32a08f6488ea23750943ded52119efd584d6`.
**Relevant component pins:** kymux `af10dbb3ea016135c0ec8e01143179ad4bda005b`, kymedia `b0efdfa251a19274ff1d9bf6324deb6bee10c026`, kyctl `92c632f9e889917a34aaa7697fb88b4991054b1c`, avconv `5ca80cca50573f212f2b20007b2642d4a7588a43`, VLC `d66cdddbfee408538a45e3e60d4f3b82a2f60b17`, vlc-rs `7cbfc51313b4bb3ab07be51505b7054e4e2c366b`, txproto `7f84b9e76bab936f57f1c184e65fb2118a020f06`.

This comparison separates inspected source/API evidence from product documentation and from assumptions that require a runnable reference proof. The A1/A2 codecs and capture helpers remain useful comparison fixtures. They are not selected as the production media architecture. The production media gate stays closed until the pinned upstream comparison and audio and video reference proofs are complete.

## Reference proof exit criteria

The mandatory **video** proof must capture a real Windows webcam, feed it through the pinned Kyber/avconv encoder and Kymux video protocol, decode and present it through the pinned Kyber/VLC client path, and report a visible frame result. It must record encoder and decoder selection, confirmed hardware acceleration or a clear unsupported reason, frame timestamps, capture-to-display latency, frame coverage, CPU/GPU and memory use. It must test whether timestamps remain aligned with simultaneous audio and report A/V drift. Run software fallback when hardware encoding is unavailable. The proof is a closed known-participant test and follows the C-1 ADR's parser-risk policy.

The mandatory **audio** proof must select a physical Windows microphone rather than system loopback, encode Opus through Kyber's graph, transport it using a pinned Kymux audio endpoint, play it using Kyber's playback path, and measure source coverage, received sample continuity, audible output, delay and resource use. Use headphones and document device selection and teardown. The unreliable VirtualBox C922 microphone is not a required input.

Run equivalent native Linux source and playback trials when its real capture device and desktop session are available. The Ubuntu VM may validate synthetic media and software decoding. Do not count VM physical microphone failure as a Kyber codec result. Do not claim cross-platform hardware support without a successful platform-specific run.

## Windows native build attempt (2026-11-22)

The pinned Windows cross-build was attempted with Meson 1.12.1, Ninja 1.13.2, pkgconf 3.0.7, NASM 2.16.02, and the installed x86_64 MinGW-w64 8.1.0 compiler. The `libavconv` and `txproto` checkouts match the revisions above. Meson configured the VPL 2.10.1 and NVENC header subprojects, then stopped while building the pinned x264 fallback. Its configure enables OpenCL, and the generated out-of-tree Makefile fails with `No rule to make target 'common/opencl/x264-cl.h'`; the header exists in x264's source tree, but this generated dependency is resolved relative to the separate build directory. The build-only `MAKE` path inherited from GnuWin32 also required overriding because it contained spaces; that override allowed configuration to reach x264.

This is a build feasibility result, not a Kyber media proof: kymedia has not completed compilation, no Skyber webcam or microphone frames were processed, and no Kyber decode or presentation was exercised. No upstream source or Skyber production code was modified to work around the x264 failure. Next investigate an upstream-supported x264 configuration that avoids the broken out-of-tree OpenCL target, or use Kyber's supported full Windows build environment. Hardware acceleration, A/V sync, latency, resource use and visible video remain unverified.

### Windows build retry

Meson 1.12.1 and Ninja 1.13.2 were installed as user tools and their versions were verified. Retrying the configured build with access to the local Lua fallback moved past the earlier Lua permission/configuration issue, but x264 still failed before producing a build graph. The generated x264 Makefile passed source paths prefixed by a long relative path ending in `/tmp/skyber-kyber-sdk-0.29.0/...`; MinGW reported that the referenced x264 source files did not exist. The same invocation reported an unrecognized truncated `-fvisibil` compiler option. This is evidence of a Windows/MSYS path or argument-translation problem in this build setup; the exact cause has not been isolated. The source-preserving OpenCL-header copy was removed when Meson recreated its generated subproject directory, so no upstream files were changed. No `build.ninja` was generated and no native libraries were produced.

### Reproducible Windows builder

The supported Kyber Debian Windows cross-build image was pulled by its digest, `registry.gitlab.com/kyber/ops/docker-images/debian-win64@sha256:39632e7b0283d5686cfae181b0c85d17b68e3a3024d4054c5eae64b80d8c9694`. In this image, Meson 1.12.1 is installed with Jinja2 3.1.6 and MarkupSafe 3.0.3, and Ninja 1.13.2 is available. The exact pinned SDK checkout and all build work live in a Docker named volume. `MESON_PACKAGE_CACHE_DIR` and `CARGO_HOME` also point into that persistent volume so a replacement container can reuse source archives and Rust downloads.

The initial disposable attempts downloaded Lua repeatedly because each `docker run --rm` discarded its checkout and Meson package cache. In the persistent-volume run, Lua was downloaded once and subsequent Meson configuration used the cached archive. Its SHA-256 matches Kyber's wrap file (`7d5ea1b9cb6aa0b59ca3dde1c6adcb57ef83a1ba8e5432c0ecd06bf439b3ad88`).

**Verified build result (2026-11-22):** the pinned SDK checkout `ebca32a08f6488ea23750943ded52119efd584d6` completed `./kyctl/build-win32.sh -d -o /tmp/skyber-rootfs`, followed by `./kyctl/build-win32.sh -s -o /tmp/skyber-rootfs build-kyclient`, in the digest-pinned Debian Windows cross-build image. The build compiled and installed Kyber's Windows media dependencies, input dependencies and `kyclient` release library. The copied, ignored `build/kyber-rootfs` contains 1,467 files (~903 MB), including `kyavserver.exe`, `kynputserver.exe`, `kyclient.dll`, `kynput.dll`, `libvlc.dll`, FFmpeg tools, static/import libraries and the three MinGW runtime DLLs required by Kyber executables. The final Kyber cargo release build completed successfully. The build emitted upstream unused-code warnings from `kynput` and a deprecated `cargo-cinstall --dlltool` warning; neither stopped the build.

The new `scripts/build-kyber-windows.ps1` entry point completed successfully against the same persistent cache volume. Its first run populated the persistent Cargo cache and downloaded Rust crates once. Later runs skipped the native dependency stage after checking the pinned rootfs outputs. Repeated unconditional Cargo invocations still recompiled the client, so the wrapper now checks for the pinned client library and DLL before building it. After that change, a warm invocation exited successfully in under five seconds without rebuilding dependencies or client artifacts.

Windows runtime smoke results: `ffmpeg.exe -version` and `ffprobe.exe -version` both succeed. Initially `kyavserver.exe` failed to load with Windows status `0xC0000139`; its PE imports include MinGW runtime DLLs absent from the install root. The builder now copies `libstdc++-6.dll`, `libgcc_s_seh-1.dll` and `libwinpthread-1.dll` from the pinned compiler sysroot. A subsequent direct launch entered application initialization and returned `IpcAddressUnavailable`. Inspection of the pinned SDK source (`kyavserver/src/main.rs` and `libkypc/process/mod.rs`) shows this executable is a child worker: Kyber's controller launches it through `ProcessFactory`, which injects `KYBER_PARENT_ADDR`. A direct launch omits that parent-provided environment and is therefore an invalid standalone smoke test. The result proves Windows DLL loading only; it neither indicates a Kyber service defect nor proves a usable media session. The next runtime check needs the controller or an IPC-compatible parent harness.

The build is not a runtime media proof. Webcam or microphone capture, Kyber encode, Kymux media transfer, decode and visible presentation, hardware acceleration, A/V synchronization, latency and resource use remain unverified.

Run `scripts/build-kyber-windows.ps1` from the Windows account that owns the Docker Desktop session. It checks Linux x86_64 engine access before creating or starting the builder. `scripts/build-kyber-windows.ps1 -Status` reports the existing persistent container and volume. If the sandboxed shell is denied access to Docker's Windows named pipe while the user session can reach it, invoke the script from that user PowerShell session. A build failure leaves the named volume, checkout, downloaded sources and compiler state available for retry.

This is build infrastructure progress, not a Kyber media proof. Webcam and microphone capture, encoding, transport, decoding, visible presentation, hardware acceleration, A/V synchronization, latency and resource use remain unverified.

## Experimental media modes

Keep `Auto (upstream-informed)` and the compatible manual protocol choices for each track. Treat unreliable microphone, GOP-streamed webcam and reliable screen share as experimental profiles. Resolve Auto deterministically from supported local modes and authenticated peer compatibility. Preserve the effective selection in diagnostics and reject mismatched or unsupported proposals before creating media endpoints. A preference change applies to the next call. Preserve reliable audio/video endpoint coverage as a regression baseline.

Compare modes using identical source, encoder, bitrate and presentation settings on direct UDP and the encrypted WebSocket relay. Include controlled loss, jitter, RTT and bandwidth limits. Measure audio glitches and underruns, video frame quality and continuity, GOP recovery time, p50/p95/p99 latency where clocks allow, CPU/GPU, memory, bandwidth and reconnect. Publish measurements before changing the Auto mapping. These profiles are experiments, not defaults.

## WebSocket decision record

The native Kyber WebSocket implementation is a promising host/client fallback in the pinned desktop product. Its existence does not prove Skyber requirements. The current evidence is insufficient to replace the functioning encrypted QUIC-over-WSS relay. Before revisiting the choice, demonstrate two authenticated Skyber peers through the candidate backend, end-to-end confidentiality from peer to peer, an opaque relay boundary, independent microphone/webcam/screen tracks, bounded queueing, disconnect/reconnect and media measurements. Retain QUIC-over-WSS until that evidence exists.
