# Kyber media upstream comparison

**Status:** Source audit in progress. Runtime capture, encode, transport, decode, presentation, synchronization and performance proofs remain open.
**Reviewed:** 2026-11-22
**SDK:** Kyber 0.29.0, SDK tag commit `ebca32a08f6488ea23750943ded52119efd584d6`.
**Relevant component pins:** kymux `af10dbb3ea016135c0ec8e01143179ad4bda005b`, kymedia `b0efdfa251a19274ff1d9bf6324deb6bee10c026`, kyctl `92c632f9e889917a34aaa7697fb88b4991054b1c`, avconv `5ca80cca50573f212f2b20007b2642d4a7588a43`, VLC `d66cdddbfee408538a45e3e60d4f3b82a2f60b17`, vlc-rs `7cbfc51313b4bb3ab07be51505b7054e4e2c366b`, txproto `7f84b9e76bab936f57f1c184e65fb2118a020f06`.

This comparison separates inspected source/API evidence from product documentation and from assumptions that require a runnable reference proof. The A1/A2 codecs and capture helpers remain useful comparison fixtures. They are not selected as the production media architecture. The production media gate stays closed until the pinned upstream comparison and audio and video reference proofs are complete.

## Component comparison

| Area | Pinned source/API evidence | Runtime status and limitations | Skyber direction |
| --- | --- | --- | --- |
| SDK composition | The SDK tag declares component repositories as Git submodules. Its license notice offers AGPLv3 and commercial terms. kymux and kymedia carry dual-license notices. | Packaged component licenses, native DLL/ELF dependencies and Qt/VLC distribution obligations need a release-specific review. | Keep pins explicit. Do not update or relicense components as part of the media proof. |
| Video transport | `kyproto::VideoProtocol` implements `Reliable`, `GopStream`, `Unreliable`, and `UnreliableFec`. `GopStream` starts a QUIC stream per keyframe, retransmits the current GOP, abandons old GOP streams, and repeats codec/configuration packets as needed. | Protocol quality, loss recovery time, and compatibility with each encoder configuration have not been measured in Skyber. Datagram/FEC behavior depends on the negotiated path and peer implementation. | Expose the pinned variants as selectable experimental modes. Test the GOP profile with periodic IDR frames and intra-refresh disabled. Keep reliable mode as a regression baseline. |
| Audio transport | `kyproto::AudioProtocol` implements `Reliable`, `Unreliable`, and `UnreliableFec`. The unreliable drivers fragment against the active transport's maximum datagram size. | Audio continuity, FEC benefit and jitter behavior are unmeasured in Skyber's call paths. | Expose all variants as selectable experiments. Compare with a fixed Opus source and controlled impairment. |
| Upstream selection defaults | `kyctl-common::KyProtoConfig` defaults both audio and video to `Reliable`. Its enums do not include Kyber WebSocket mode because WebSocket endpoints are separate. | These are the stock client defaults, not proof that reliable mode is optimal for Skyber conversations. Product documentation about low latency does not override the pinned enum defaults. | Skyber `Auto` must be labeled upstream-informed and resolved explicitly. Do not mark any experiment profile as an established default until comparable Internet measurements support it. |
| GOP/keyframes | The pinned kyctl controller detects `GopStream` and forces `intra_refresh` off because GOP boundaries require periodic IDR frames. | A compatible Skyber encoder profile, keyframe interval and recovery time remain to be verified on hardware encoders and software fallback. | Share validated codec/keyframe settings in authenticated call negotiation. Reject incompatible combinations before media endpoints start. |
| Capture and encoding backend | At this pin, `kyavservice` defaults to `Txproto`; `Libavconv` is an alternate backend. The Kyber 0.28 release note calls avconv a preview while txproto remains default/fallback. `kyavservice` source contains encoder selection, clock setup, capture, encode and Kymux sink components. | The exact desktop production configuration, device enumeration, capture consent, hardware choice, timestamp behavior and cancellation have not been exercised by Skyber. | Audit the txproto and avconv production configurations before choosing a backend. Reuse Kyber's graph and sink APIs wherever practical. |
| Opus and source audio | The pinned avconv audio service captures an audio-loopback source, converts to stereo 48 kHz float, and configures `libopus` at 128 kbit/s with 20 ms frames. The native WASAPI provider enumerates both render-loopback and capture/microphone endpoint classes. The PulseAudio provider represents microphone inputs separately from sink monitors. | The stock avservice path is system loopback, not a user-selected microphone API. Selecting a physical microphone and preventing playback feedback require an explicit source choice and a device trial. | The audio proof must select a microphone source, encode through Kyber's graph, carry packets over Kymux, and play through the Kyber client path. Keep A1/A2 synthetic tone fixtures for regression. |
| Webcam and screen acquisition | The avconv source API can enumerate native sources and its source-node API accepts caller-submitted raw frames or coded packets. Kyber documents Windows/Linux encoder choices. On Linux, the pinned avconv config includes GStreamer sources that can supply raw frames or encoded H.264/HEVC. The existing Skyber Windows Media Foundation helper produces webcam frames that can be adapted into avconv. | The pinned kyavservice configuration path inspected here focuses on screen and system audio. A direct webcam source and its device-selection UI are not proven. Actual source format conversion, permissions, device loss and lifetime remain runtime work. | Build a narrow Windows camera-to-avconv input adapter, then prove webcam → Kyber encode → Kymux → Kyber decode → visible presentation. Evaluate a separate narrow device adapter for microphone selection. Keep webcam and screen share independent. |
| Codec and acceleration | The pinned server configuration documents NVENC and x264 on Windows/Linux, with AMF and QSV marked experimental on Windows and VAAPI marked experimental on Linux. The pinned encoder source maps additional hardware codec names. Kyber 0.28 introduced the avconv backend while retaining txproto as default/fallback. | Availability is dependent on device, driver, build features and chosen backend. No Skyber trial currently proves hardware acceleration, CPU fallback, quality or resource cost. | Record actual selected encoder/decoder and hardware use for every proof run. Measure CPU/GPU, memory, bitrate, latency, frame loss and recovery. Treat the platform's advertised choice as documented support, not local runtime evidence. |
| Timestamps and synchronization | The pinned avconv service has `ZeroedOrigin` and `System` clock configuration and aligns audio/video capture clocks. Kyber's controller starts a Kymux clock-sync endpoint. `kyvlcplayer` reports PTS and frame-displayed metrics and gives audio clock-master selection to VLC. | Skyber has not verified common-clock capture, drift, end-to-end A/V synchronization, or Qt presentation timing. | Preserve source timestamps through the proof. Measure audio/video drift and presentation delay under load before selecting the player integration. |
| Decode and playback | kyctl's desktop backend registers Kymux endpoints with `kycom`, obtains local stream URLs and starts `kyvlcplayer`. The VLC player enables low-delay and zero network-caching options, accepts video/audio buffer overrides, and embeds video into Win32 HWND or X11 XWindow handles. | This is a viable native-window integration candidate, not proof of Qt Quick surface compatibility, Wayland embedding, zero-copy GPU presentation, or suitability for Skyber's floating-window design. | Test a minimal Qt-owned native handle on Windows and X11. Measure copies, render delay and stability. Decide Qt/Wayland/GPU architecture only after the mandatory video proof. |
| Native WebSocket | Kyber 0.29 adds native `tungstenite` support and separates WebSocket endpoints for video, audio and input. The inspected kyctl client connects to host-owned media URLs with a pinned TLS certificate hash and session cookie. The pinned controller rejects more than one video stream over this backend. | The observed design is client-to-host. The source reviewed does not establish two-peer session semantics, opaque-relay end-to-end encryption between invite identities, or two independent video tracks. A native WebSocket layer terminates its own TLS and does not inherently forward Skyber's peer QUIC packets. | Keep the functioning encrypted QUIC-over-WSS relay during C-1. Build a separate compatibility analysis of authentication, encryption termination, bidirectional peer roles, track count, reconnect and metadata before any long-term transport choice. |
| WebSocket relay and Kymux | Skyber's current WSS relay forwards bounded encrypted Quinn datagrams and the ICE/Quinn proof carries a pinned Kymux stream through it. | This proves local transport framing and handshake behavior, not public relay deployment, production capacity or media latency. | Preserve the current relay, its tests and its end-to-end encrypted-packet boundary while collecting native-WebSocket evidence. |

## Reference proof exit criteria

The mandatory **video** proof must capture a real Windows webcam, feed it through the pinned Kyber/avconv encoder and Kymux video protocol, decode and present it through the pinned Kyber/VLC client path, and report a visible frame result. It must record encoder and decoder selection, confirmed hardware acceleration or a clear unsupported reason, frame timestamps, capture-to-display latency, frame coverage, CPU/GPU and memory use. It must test whether timestamps remain aligned with simultaneous audio and report A/V drift. Run software fallback when hardware encoding is unavailable. The proof is a closed known-participant test and follows the C-1 ADR's parser-risk policy.

The mandatory **audio** proof must select a physical Windows microphone rather than system loopback, encode Opus through Kyber's graph, transport it using a pinned Kymux audio endpoint, play it using Kyber's playback path, and measure source coverage, received sample continuity, audible output, delay and resource use. Use headphones and document device selection and teardown. The unreliable VirtualBox C922 microphone is not a required input.

Run equivalent native Linux source and playback trials when its real capture device and desktop session are available. The Ubuntu VM may validate synthetic media and software decoding. Do not count VM physical microphone failure as a Kyber codec result. Do not claim cross-platform hardware support without a successful platform-specific run.

## Experimental media modes

Keep `Auto (upstream-informed)` and the compatible manual protocol choices for each track. Treat unreliable microphone, GOP-streamed webcam and reliable screen share as experimental profiles. Resolve Auto deterministically from supported local modes and authenticated peer compatibility. Preserve the effective selection in diagnostics and reject mismatched or unsupported proposals before creating media endpoints. A preference change applies to the next call. Preserve reliable audio/video endpoint coverage as a regression baseline.

Compare modes using identical source, encoder, bitrate and presentation settings on direct UDP and the encrypted WebSocket relay. Include controlled loss, jitter, RTT and bandwidth limits. Measure audio glitches and underruns, video frame quality and continuity, GOP recovery time, p50/p95/p99 latency where clocks allow, CPU/GPU, memory, bandwidth and reconnect. Publish measurements before changing the Auto mapping. These profiles are experiments, not defaults.

## WebSocket decision record

The native Kyber WebSocket implementation is a promising host/client fallback in the pinned desktop product. Its existence does not prove Skyber requirements. The current evidence is insufficient to replace the functioning encrypted QUIC-over-WSS relay. Before revisiting the choice, demonstrate two authenticated Skyber peers through the candidate backend, end-to-end confidentiality from peer to peer, an opaque relay boundary, independent microphone/webcam/screen tracks, bounded queueing, disconnect/reconnect and media measurements. Retain QUIC-over-WSS until that evidence exists.
